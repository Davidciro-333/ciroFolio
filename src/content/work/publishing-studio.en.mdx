## The brief

The team at Galactic AIMA records videos every week and was publishing them by hand: open
Business Suite, upload, paste the copy, pick a time, repeat for each network. I had already
solved the publishing half of that problem for my own content pipeline, beBetterStudio: a
queue, an n8n scheduler that drains it, tokens that rotate themselves, notices on Telegram.

The ask was that half, without the video generator, for several people at once: upload what
you recorded, put it on a calendar, forget about it.

## Spec before code

I wrote the specification first: every post and per-network state with its transitions, the
contract between the app and n8n, the contract with Telegram, the scheduled jobs, the
environment variables and the test strategy. Meta's requirements were checked against the
official documentation before a line was written: Facebook Reels only accepts 3 to 90
seconds, and a Page can publish 30 posts in 24 hours.

The test strategy included a fake n8n. That let the first four phases (sign-in, uploads,
posts, calendar, the internal API with leases and retries) be built and tested with no Meta
account involved at all. When the real integration arrived, it was the last piece, not the
first unknown.

It is a TypeScript monorepo: React and FullCalendar on the front, Express with PostgreSQL on
the back, Google sign-in, and a bucket that is private end to end. The browser, ffprobe and
Meta itself all read the video through signed URLs.

## The decision that mattered: who owns the state

The easy version puts the logic in n8n: a workflow reads the queue, publishes, and marks the
row. It works until something dies halfway. Then n8n holds half the truth, the database holds
the other half, and nobody can say whether a video went out.

So n8n holds nothing. It asks the app for work, and the app hands it out with
`FOR UPDATE SKIP LOCKED` and a 15-minute lease. Progress renews the lease, the result closes
the attempt, and a job marks any expired lease as a timeout. Every attempt and every state
change goes into two append-only logs, so the history of a post can be read, never edited.

The subtle case is a success that arrives after a timeout, with the same claim. That one is
accepted as published, on purpose: otherwise the retry publishes the same video twice, and a
duplicate on a client's feed is worse than a late status.

A post also has one target per network, and its state is derived from them. Instagram can be
published while Facebook is retrying; cancelling stops what can still be stopped and leaves
what is already live alone.

## Deployment

It shares a small ARM instance on AWS with another service, behind that service's nginx,
separated by host name. The internal API only accepts requests from the n8n server's IP.
Secrets live in Parameter Store, not on disk in the repo. The database is dumped every
morning to object storage with 30 days of retention, and if a dump is missing for two days an
alarm fires: a backup that nobody checks is a hope, not a backup.

## Where it stands

In production since October 31, 2026. The first reel published itself to Instagram and
Facebook on the first attempt, one minute apart. Since then it has gained AI-assisted copy
with automatic comment keywords, free time slots, batch scheduling and an upload path that a
creator can trigger from Claude with a personal key. 277 automated tests, all green.

What is deliberately not there yet: YouTube and TikTok are prepared but not connected, and
it runs as a single instance for a single team. Opening it to other businesses means
Facebook Login for Business and Meta's App Review, which is a product decision before it is
a technical one.
